# MAP — Kingshot_Toolbox

> Cartographie du projet. **Point d'entrée avant toute tâche** : lis ce fichier, puis n'ouvre que les fichiers concernés.

---

## 1. Vue d'ensemble

- **Live** : https://kingshottoolbox.com/
- **Repo** : `Aistra91-KS/Kingshot_Toolbox` (anciennement `Hub-Kingshot` : `/hub-kingshot/` → `/Kingshot_Toolbox/` sur GitHub Pages, puis la **racine** de `kingshottoolbox.com`). Le site ne dépend plus de son chemin de déploiement — cf. la règle `<base href>` relatif au §9.
- **Type** : site statique hébergé sur **GitHub Pages** (pas de backend, pas de build).
- **Stack** : HTML / CSS / JS **vanilla** (aucun framework, aucun bundler) + **GitHub Actions** (notif Discord).
- **Langues** : **FR / EN**, bascule à chaud (aucun rechargement).
- **Architecture** : Hub (catégories) → Outils. Site mono-jeu (Kingshot). Toute la navigation est pilotée par un manifeste unique `js/site-config.js`.
- **Persistance** : `localStorage` uniquement (clés centralisées dans `js/storage-keys.js`), export/import JSON via `js/backup.js`.

## 4. Système bilingue (i18n)

Deux mécanismes, tous deux réagissant à l'event global **`langChanged`** émis par `GlobalLang.set()` :

1. **Dictionnaire + `data-i18n`** (pages outils) :
   - Chaque script de page déclare un objet `const i18n = { FR:{clé:…}, EN:{clé:…} }`.
   - Dans le HTML : `<span data-i18n="clé">…</span>` (et `data-i18n-placeholder="clé"` pour les inputs).
   - `GlobalLang.applyI18n(i18n[lang])` remplace `textContent` / `placeholder`.
2. **Attributs inline `data-en` / `data-fr`** (pages `database/buildings/*`) :
   - `<td data-en="Bread" data-fr="Pain">Pain</td>` — un petit script inline applique `data-<lang>` sur `[data-en][data-fr]`.

**Langue du HTML servi = anglais.** Le texte écrit en dur dans les fichiers `.html` (et `<html lang="en">`) est celui de la langue **par défaut**, `EN` — le français est appliqué par le JS au chargement. C'est ce qu'exige le référencement : Googlebot indexe le rendu, qui est anglais, et un HTML français sous un `<title>` anglais envoyait des signaux contradictoires. Conséquence à connaître : un visiteur ayant choisi `FR` voit brièvement l'anglais avant la bascule (~40 ms en conditions normales, jusqu'à ~3 s en 3G bridée) — c'est le même phénomène qu'avant, dans l'autre sens, quand le HTML était français et la majorité des visiteurs en anglais. **Toute nouvelle page s'écrit donc en anglais en dur**, avec les `data-i18n` / `data-fr` qui portent la traduction.

**Exception — pilote « une URL par langue » (`fr/shop/theater-shop.html`).** Le modèle ci-dessus sert UN html anglais que le JS traduit : Googlebot, qui n'a pas de préférence, n'indexe donc jamais que l'anglais, et le contenu français n'existe pour lui nulle part. La page du Magasin du Théâtre teste l'autre approche, celle que Google attend d'un site bilingue : **deux adresses, une par langue**, qui se citent par `hreflang` (`en`, `fr`, `x-default` → EN) et portent chacune son propre `canonical`. La jumelle française est du HTML français en dur, `<html lang="fr">`, `<base href="../../">`.

Le basculement se joue en **six lignes inline dans la page `/fr/`**, jamais dans `lang.js` (60 autres pages en dépendent) :
- `GlobalLang.get()` est réécrit pour renvoyer `FR` — header, footer, tableau et boutique s'affichent en français **quelle que soit la préférence enregistrée du visiteur** : ici c'est l'URL qui décide, pas la préférence.
- `GlobalLang.set('EN')` ne retraduit pas la page, il **emmène vers la jumelle anglaise**. C'est ce que doit faire le bouton de langue dès qu'une langue = une adresse ; sans cela le bouton semblerait cassé.
- la préférence globale n'est écrite (`FR`) que si le visiteur **n'en avait aucune** : arriver par la porte française règle le site en français, mais un choix déjà fait est respecté.

La page anglaise, elle, ne change pas de comportement : un visiteur réglé en `FR` la voit toujours traduite par le JS. **Portée : cette page seulement.** Ne pas généraliser sans mesurer — chaque page dupliquée est une page à maintenir en double.

**Langue** : stockée sous `hub_lang` (clé propre à `GlobalLang`, défaut `EN`). Sur desktop, le header expose un **bouton rond « globe + code »** (`.app-header-lang`, jumeau visuel du bouton thème) qui bascule FR⇄EN via `GlobalLang.set()` (`hdrInitLangToggle`/`hdrUpdateLangCode` dans `header.js`) ; sous 820px et en mode condensé il est masqué (langue reprise dans le drawer / le panneau profil). Les boutons `.lang-btn` du hub restent synchronisés via `GlobalLang.applyToButtons` (`applyToSelect` demeure un utilitaire générique, plus utilisé par le header).

**Où ajouter une clé** :
- Page outil → ajoute la clé dans les blocs `FR` **et** `EN` de l'objet `i18n` du script concerné, puis pose `data-i18n="clé"` dans le HTML.
- Page bâtiment → soit ajoute au `dict {FR,EN}` inline + `data-i18n`, soit utilise directement `data-en`/`data-fr` sur l'élément.
- Libellé de navigation (nom d'outil/catégorie) → dans `site-config.js` (`name: {EN, FR}`), jamais en dur.

- **le nombre de transformations n'a plus de boucle 0..100** : pour un plan donné, `transfosNecessaires()` donne en O(1) le minimum de transformations qui le finance (les deux stocks étant monotones). Le bloc TRIM ne s'applique donc plus aux plans exacts ;
- **la règle des files borne la profondeur** : le plan s'arrête dès 2 constructions lancées sans accélérateurs.
Le score ne dépendant pas de l'ordre, `regrouper()` réordonne le plan pour qu'il se lise en quelques séries (cf. `.tg-plan`) et `rejouer()` valide le résultat — sinon on garde l'ordre brut. **Garde-fou** : au-delà de `KVK_MAX_ETATS` (60 000) on rend la main au glouton, qui rejoue alors ses 3 stratégies **plus une variante par bâtiment écarté** (l'astuce manuelle du joueur, automatisée). Mesures : médiane 16 états, p99 21 000, `runCalculator` ~25 ms au pire sur 250 scénarios, ~150 ms sur les cas extrêmes qui déclenchent le repli.

**Optimiseur Académie de Guerre — mode KVK** (`wa_optimizer.js`) : **reste glouton** (un niveau à la fois, pas de retour arrière) — contrairement à TrueGold, l'exhaustif est hors de portée : les 3 arbres dépassent **2 millions d'états** dès 3 000 poussière, là où TrueGold en compte une centaine. Le mode KVK garde donc le meilleur plan parmi plusieurs candidats (`KVK_ORDERS`), et le même piège qu'à TrueGold y était présent : on gagnait des points en **décochant un arbre**. Deux ajouts le corrigent :
- **Ordre `'chain'`** : un niveau verrouillé par un *prérequis* (pas par le palier d'Académie, qui ne s'achète pas) est valorisé comme un **paquet** — tous les niveaux manquants + lui-même — dont la densité (points/poussière) est portée par sa première marche jouable. Sans ça le glouton ne pouvait jamais investir dans une suite de niveaux médiocres qui ouvre une bien meilleure affaire : le **nœud de palier de troupe** vaut 2 765 pts/poussière (le meilleur de la base) mais se cache derrière ~8 600 poussière de niveaux à 1 631 (les pires). Face à trois arbres quasi symétriques, l'ancien glouton entamait les trois chaînes et n'en finissait aucune. La part déjà payée sortant du calcul, une chaîne entamée devient de plus en plus attractive → elle est terminée. **Deux garde-fous obligatoires** : ne s'engager que si le paquet tient dans le budget restant **de poussière ET d'accélérateurs**, et ne retenir comme première marche qu'un niveau *appartenant* au paquet (un prérequis déjà satisfait est enregistré à coût nul, son niveau suivant est hors paquet et donc non financé).
- **Relance sur chaque arbre seul** : le plan optimal **concentre** — à 15 000 poussière il met 13 540 dans un arbre et laisse les deux autres au minimum. Aucun glouton réparti ne propose ça ; le même glouton limité à un arbre, si. Coût borné : 4 ordres × (1 + nb d'arbres) plans.

**Rôle de chaque mode (Académie de Guerre) — tranché par Paul, ne pas « corriger » l'un en l'autre** : *Max recherches* vise le **nombre** de recherches (il touche donc naturellement plusieurs arbres, les niveaux bon marché étant partout) ; *KVK* vise **les points, point final** — si le meilleur plan ne touche qu'**un seul** des arbres cochés, c'est la bonne réponse, pas un bug (la chaîne du palier de troupe ne paie qu'une fois terminée). Cocher un arbre dit « tu peux t'en servir », jamais « tu dois ». *Score cible* vise le moindre coût pour atteindre un score.

Résultat : **+4 à +6,5 %** de points dans la plage concernée, à ≤ 0,4 % de l'optimum réel (sauf gros budgets, ~1,8 % restants) ; sur 600 scénarios aléatoires, 123 améliorés (+12 % en moyenne) et **aucune régression**. Coût : 2 à 16 ms dans Chromium, derrière le debounce de 160 ms de la page. Les modes *Classique* et *Score cible* ne passent pas par ce chemin et rendent une sortie **identique**. *(Note : l'en-tête du module affirmait que le temps ne contraignait qu'en mode Classique — faux depuis plusieurs versions, corrigé.)*

**Portraits d'Experts — deux jeux d'images selon la taille d'affichage** :
- `img/Master/<Nom>.webp` (96–124 px) : vignettes d'origine, utilisées par les pages `database/masters/*` qui les affichent en 84–92 px. Nettes à cette taille, et légères. **Ne pas les remplacer.**
- `img/Master/hd/<Nom>.webp` (600×800) : portraits pleine page pour `masters.html` seul, servis par le helper `masterPortrait()` de `js/masters.js`. Le cadre `.master-portrait` fait 320 px de haut (et `#modal-header-bg` 400×150) : les vignettes d'origine y subissaient un agrandissement ×2,6 à ×3,2, d'où la pixellisation — que des `filter: blur()` masquaient au prix d'une image floue (supprimés).
- **Ratio 3:4 imposé** : `.master-portrait` fait 240×320, donc une source 600×800 n'est pas recadrée par `background-size: cover`. Les captures de jeu n'ont pas ce ratio ; elles sont calées en *contain* puis les bandes manquantes sont comblées en moyennant les pixels du bord (le fond doré est un dégradé lisse, la jointure est invisible). Rogner quelques pixels de bordure sur la source est nécessaire : les captures portent des salissures collées au cadre qui ressortiraient à la jointure.

**Boutiques — une page par boutique (`shop/*.html`)** : structure calquée sur `database/*` mais **hors** de `database/` — ces pages portent de l'état utilisateur (monnaie, stock restant) et chargent donc le socle complet (`storage-keys` → `profiles` → `help` → `backup`), là où les pages BDD sont en lecture pure. Conventions :
- **`shop_calc.html` reste l'URL du sommaire** (déjà indexée, référencée par `site-config.js`) : elle a changé de rôle, pas d'adresse. Trois familles y sont listées — Événement / Permanentes / Coffres — plus **deux** accès aux référentiels : `shop/items.html` (gemmes, éditable) et `shop/items-euro.html` (prix réel, lecture seule). Les deux cartes sont écrites **en dur** dans `shop_calc.html`, comme le reste du maillage interne.
- **Les cartes du sommaire sont écrites en dur** (liens, noms, monnaies via `data-en`/`data-fr`), comme les sommaires `database/*/index.html` : le maillage interne doit exister sans exécuter le JS. `shop_calc.js` n'hydrate que ce qui dépend des données ou de l'heure (vignette, nombre d'objets, badge de statut) puis réordonne les événements.
- **Une page boutique** = `<base href>`, `title`/`meta description`/`h1`/intro **en dur** (jamais reconstruits par le JS, sinon le bouton d'aide accroché après le `h1` saute au changement de langue), plus `window.SHOP_SLUG` ; tout le reste est rendu par `shop-page.js` dans des conteneurs vides (`#sp-thumb`, `#sp-facts`, `#sp-actions`, `#sp-cart`, `#sp-podium`, `#sp-table`, `#sp-switch`). Le bouton d'aide est ancré sur `#sp-facts`. Les raccourcis vers les autres boutiques (`#sp-switch`, classe `db-switch footer`) sont **sous le tableau** : on choisit une autre boutique après avoir lu celle-ci, pas avant. Juste au-dessus, le bloc `.sx-reflinks` — **écrit en dur dans les 16 pages** (maillage sans JS, cf. §9) — mène aux deux référentiels de valeurs : 💎 « Valeur des objets » (gemmes) et € « Prix réel des objets ». C'est la réponse au joueur qui doute d'un chiffre du tableau, placée là où la question se pose. Les deux pastilles reprennent les couleurs des deux lectures de la page (turquoise / or) ; le filet horizontal du bas de page est porté par `.sx-reflinks`, la nav qui suit perd le sien pour qu'il n'y ait qu'un trait.
- **Titre d'une boutique d'événement** : `Kingshot <boutique> - Best Deals & Gem Value`. Le titre mène par le **bénéfice** — ce que la page permet de décider —, pas par la monnaie : « <Monnaie> Costs » décrivait ce qu'on *paie* et non ce que la page apporte (classement au ratio, podium, stock restant, panier), et dépensait un tiers des ~60 caractères que Google affiche pour un terme qu'un joueur ne connaît **qu'une fois déjà dans l'événement**. La monnaie reste indexée par la `meta description`, l'intro, la barre de faits et l'en-tête du tableau : la sortir du titre ne la fait pas disparaître. Le **nom de l'événement** entre dans le titre quand il diffère de celui de la boutique (`Blizzard Shop` → titre `Blizzard Brawl Shop`, l'intro et la description nommant l'événement dans les deux langues) : c'est la requête la plus cherchée. Le `h1` et le fil d'Ariane, eux, gardent le nom **in-game** de la boutique.
- **Le contenu d'une boutique est un tableau, une ligne par objet** (`table.sx-table`) — pas une grille de cartes : à surface égale il montre 3 à 4 fois plus d'objets, et les colonnes se comparent en diagonale. Les colonnes racontent trois blocs : *ce que ça coûte* (Qté, Coût) → *ce que ça vaut* (Valeur gemmes, Ratio) → *ce que tu peux en tirer* (Restant, Max fin, Obtenable, Coût obt., événements seulement, séparés par un filet `.sep`). Seul le podium des 3 meilleures affaires garde des visuels.
- **Mode édition (crayon)** : les boutiques d'événement restent ajustables — quantité, coût, stock restant, ajout et retrait d'objets, réinitialisation à la version du fichier. Ces champs n'apparaissent **que** dans le mode édition (`SP_EDIT`, volontairement non persisté : personne ne doit rester en édition sans le savoir), déclenché par le bouton `.sx-edit-toggle`. La colonne de suppression est `position:sticky; right:0` — une action qui sort du champ au scroll horizontal est une action perdue.
- **Panier / budget (boutiques d'événement)** : `si.take` = nombre de **lots** retenus (un objet se vend souvent par lot, d'où la colonne « Qté » qui reste la taille du lot). `scComputeRows()` calcule en **deux passes** — d'abord le coût de la sélection, ensuite seulement le `canTake` de chaque ligne, qui dépend du solde restant donc de toutes les autres lignes. Quatre tuiles en tête (`#sp-cart`) : monnaie, dépensé, **restant**, valeur obtenue. Panier et mode édition **s'excluent** : l'un consomme la boutique, l'autre la corrige. Pas de remplissage automatique — écarté par Paul : le joueur choisit lui-même.
- **Re-rendu après saisie** : `spAfterEdit()` diffère la reconstruction d'un tick (`setTimeout 0`), et `spSnapshotTable()`/`spRestoreTable()` remettent en place le **défilement du `.table-container` et le focus** (`[data-i]` + `[data-role]` sur les contrôles du panier) : sans eux, chaque clic sur le « + » d'une ligne du bas ramenait le tableau en haut et faisait perdre le bouton sous le curseur. Remplacer le tableau depuis le `change` d'un champ détruit ce champ pendant que le navigateur traite son `blur` — ce qui lève une DOMException. Le report coalesce aussi les appels rapprochés.
- **Largeur de page — piège** : `body:not(.hub-body)` est en `display:flex` (style.css §282, héritage des pages calculateur à sidebar). Un `.db-page` sans largeur explicite y devient un **flex item dimensionné par son contenu** : sa largeur ne suit plus l'écran, et `repeat(auto-fill, …)` — qui exige une largeur connue — retombe sur **une seule colonne**. Le symptôme est sournois : le nombre de colonnes dépendait des **polices du système** (3 sous Linux, 1 sous Windows, à code identique). `shop.css` corrige avec `body:not(.hub-body) .db-page { width:100%; min-width:0 }`. Les pages `database/*` ont le même défaut latent, masqué par leurs tableaux larges qui forcent la largeur.
- **Récapitulatif du panier (`.sx-cartbar`)** : barre `position:sticky; bottom:0` placée **hors du `<table>`**, après `.table-container`. Ne pas la remettre en `<tfoot>` : Chromium ne colle un `tfoot` sticky qu'une fois le défilement entamé, donc elle serait invisible à l'arrivée sur la page. Son contenu est **aligné à gauche** parce que `.backup-fab` (style.css) est en `position:fixed` à droite avec `z-index:9000` et passera toujours devant.
- **Largeur des tables** : `style.css` cale les tables BDD sur leur contenu (`.db-section table.db-table { width:auto }`) ; `shop.css` rétablit `width:100%` pour `.sx-table` et laisse la colonne du nom absorber le reste, sinon une boutique à 6 colonnes laisse la moitié de la page vide.
- **Événement terminé = page conservée**. Supprimer une URL indexée est le seul vrai dégât SEO possible ici, et les boutiques reviennent d'une saison à l'autre. La carte du sommaire passe en grisé (`.sx-card.is-ended`, vignette en `grayscale`) **et reste cliquable** ; la page affiche un bandeau d'archive. Ajouter une boutique = 1 entrée JSON + 1 page + 1 carte au sommaire + 1 ligne `sitemap.xml` + 1 lien dans `llms.txt`.
- **Vignettes** : `img/shops/<slug>.webp` si le fichier existe, sinon **mosaïque de secours** des 4 objets de plus forte valeur de la boutique (`scThumbHtml`) — l'image réelle recouvre la mosaïque, un `onerror` la retire si elle manque. Aucune image à produire pour que le sommaire soit présentable.
- **Compte à rebours** : `scTimeLeft()`/`scTimeLeftTxt()` (affichage en J+H, rafraîchi chaque minute sur `[data-ends-at]`) est **distinct** de `scResetsLeft()` (nombre de réinitialisations 00h UTC restantes, qui multiplie le stock des objets à reset quotidien). Ne jamais fusionner les deux : l'un est cosmétique, l'autre entre dans les calculs.

**Valorisation d'un événement (`js/shop-event.js`, section `#sp-event`)** — répond à « ce que l'événement m'a coûté vs ce qu'il m'a rapporté », en % d'argent réel. Une boutique n'a cette section que si `data/events/<slug>.json` existe **et** que sa page charge `shop-event.js` (aujourd'hui : Stand d'Aventure seul). Conventions :
- **Module optionnel, jamais bloquant** : au chargement, le module `fetch` son fichier ; en 404 il s'arrête sans rien afficher. `shop-page.js` ne le connaît que par `window.ShopEvent` (fonction `spNotifyEvent()` appelée dans `spRenderAll()` / `spAfterEdit()`) : une page boutique sans le script se comporte exactement comme avant. Le garde-fou de `seAfter()` est obligatoire — `spRenderAll()` s'exécute **avant** que le module ait fini de charger.
- **Le % vit entièrement dans l'échelle € / $** : dépense et valeur sont dans la même devise, donc la règle « aucun taux gemme↔euro » (§9) est respectée. La valeur en gemmes est affichée à côté, jamais divisée par la dépense. Un joueur sans achat n'a **pas** de % (division par zéro) : la tuile affiche « F2P ».
- **Le panier de la boutique compte dans la valeur** : c'est lui qui donne une valeur aux pièces d'événement (elles n'en ont aucune en propre — le JSON ne leur donne ni `gemValue` ni prix). D'où la notification croisée ci-dessus : tout geste sur le panier recalcule la section.
- **Crans de couleur du %** (`seTier`, décidés par Paul) : < 100 rouge · 100–120 orange · 120–140 neutre · 140–180 vert clair · 180+ vert. Le libellé (« Mauvaise affaire » … « Excellent ») accompagne **toujours** la couleur : jamais d'information portée par la seule teinte. Teintes propres au bloc en `.sxe-t-*` — le rouge `#e5484d` du reste de la page ne tient que 4,2:1 sur fond sombre et l'orange `--warning` que 3,4:1 en thème clair, insuffisants pour la réserve en 11px.
- **Montants en argent réel : `seFmtMoney()`, 2 décimales fixes** — surtout pas `scFmtEur()`, dont les décimales adaptatives sont faites pour des valeurs *unitaires* d'objet : un pack à 119,99 € s'y affichait « 120 € » et un pack à 0,99 $ « 0,990 $ ». `scFmtEur()` reste en usage pour la valeur des lots dans le détail des gains, par cohérence avec le tableau de la boutique.
- **Détail des gains : colonne « Provenance »** — chaque apport est tracé à la source dans `seAdd()` (5ᵉ argument) et la cellule (`seSrcCell`) montre les **deux plus gros apports en pastilles** + un « +n » tiret é, le détail complet vivant dans l'info-bulle de la case : une ligne de tableau n'a pas à devenir un paragraphe. Le tableau s'ouvre sur une **ligne de total** (gemmes + € des seules lignes cochées) et chaque objet porte une **case à cocher** : décoché, il reste listé (grisé, valeurs barrées) mais sort du total ET de la valorisation — exclusions persistées par événement (`excluded` dans le plan, clé = itemId ou `x:<label EN>` pour un objet hors référentiel ; les monnaies n'ont pas de case, rien à retirer). Piège de largeur : `.sx-table` élargit sa **2ᵉ colonne** à 100 % (le nom, dans une boutique) — ici la 2ᵉ colonne est « Qté », d'où le correctif `.sxe-rewards` qui rend la largeur à la Provenance, sans quoi les pastilles s'empilent et triplent la hauteur des lignes.
- **Report du budget explicite** : le bouton « Utiliser comme budget » recopie les pièces prévues dans « Ma monnaie » du tableau. Jamais automatique — la saisie du joueur ne s'écrase pas en silence.
- **Placement : sous le tableau** (décision de Paul). On lit d'abord la boutique, on fait les comptes ensuite.
- **Point d'extension `window.seExtras(host, c)`** : à la fin de `seRender()`, si une page a posé cette fonction, elle est appelée avec le nœud de la section et le calcul complet — **avant** la remise du focus, pour que les contrôles ajoutés en profitent aussi. C'est par là que le Théâtre greffe son optimiseur sans toucher au reste (7 lignes ajoutées à `shop-event.js`). **`seCompute(upTo)`** accepte une borne optionnelle : ce que le plan a versé aux `upTo` PREMIERS jours de l'événement, packs des jours suivants exclus (omise, le comportement est celui d'avant — tout l'événement). Exposée par `ShopEvent.compute(upTo)`, elle évite à un greffon de recopier les règles de la boutique pour distinguer « ce que j'ai déjà » de « ce que le plan versera encore ». Un module greffé ne recalcule rien : il lit `c`, et se redessine **seul** depuis son dernier `c` quand ce sont SES saisies qui changent — repasser par `ShopEvent.refresh()` rejouerait toute la valorisation pour rien. Il lui revient en revanche de restaurer le focus et l'état de ses `<details>`, que `seRender()` ne connaît pas. **Déplacer un contrôle de la boutique dans son propre bloc** est permis et préférable à le recopier — le nœud conserve ses gestionnaires — mais il faut le **détacher avant** d'écraser son `innerHTML`, sinon le module détruit en se redessinant un contrôle qui ne lui appartient pas.
- **Ajouter un événement** = 1 fichier `data/events/<slug>.json` + `<div id="sp-event"></div>` sous le tableau + `<script src="js/shop-event.js">` après `shop-page.js`. Rien d'autre : le module lit la boutique pour la monnaie et les libellés. Deux événements sont branchés (Stand d'Aventure, Caravane du Dragon).

**Modales de détail (Caserne / Experts)** : tiroir latéral 400px sur desktop, plein écran + onglets sous 820px. Les sections de `#modal-body` portent `data-mtab="<clé>"` ; `js/modal-tabs.js` génère la barre `.mtabs` et n'affiche qu'un panneau à la fois (classe `.mtab-on`). Un panneau vide masque son onglet. Ajouter une section = poser `data-mtab` + déclarer la clé dans `PAGES` du module.

## 7. Automatisations (GitHub Actions)

Un seul workflow : **`discord-announce.yml`** (annonce Discord rédigée à la main, plus aucune traduction automatique).
- **Déclencheur** : push sur `main` touchant `.github/news/announce.md` (= committer ce fichier publie l'annonce) + `workflow_dispatch` avec entrée `dry_run` (aperçu sans envoi).
- **Mécanique** : `announce.js` lit `.github/news/announce.md`, extrait l'en-tête `<!-- kshub-news … -->` et les sections `## FR` / `## EN`, et POST un message à 2 embeds sur le `DISCORD_WEBHOOK` (`secrets`). Les commentaires HTML ne sont jamais publiés → gabarit vide = aucun envoi.
- **Pointeur** : la clé `covers-until` (SHA) de l'en-tête indique jusqu'où portait l'annonce précédente. Elle sert à lister les commits à couvrir au moment de rédiger la suivante. Aucun cache Actions, aucun commit de bot.
- **Clés d'en-tête** : **`version` (obligatoire)**, `covers-until`, `generated`, `ping` (mention, optionnel), **`ping-fr` / `ping-en`** (mention propre à chaque langue), `color` (hexa, défaut `F5B840`), `title-fr`, `title-en`.
- **Verrou changelog** : `version` doit désigner une entrée existante de `data/changelog.json`, sinon **`announce.js` refuse de publier** (code 1, message indiquant quoi corriger et les versions connues) — annonce Discord et page « Nouveautés » couvrent le même périmètre. `version: none` est l'échappatoire assumée pour une annonce qui ne touche pas au site. En aperçu (`dry_run`) le contrôle avertit sans bloquer, et un gabarit vide sort avant le contrôle (donc sans erreur). Quand la version est reconnue, le script ajoute **automatiquement** le lien `changelog.html#v<version>` en fin de chaque embed : ne pas l'écrire à la main.
- **Mentions** : la mention vit dans le `content` du **message**, jamais dans l'embed (une mention écrite dans un embed s'affiche mais **ne notifie personne**). Un message ne portant qu'un seul `content`, renseigner `ping-fr` et/ou `ping-en` **force l'envoi en deux messages** (FR puis EN), chacun avec sa mention. La clé `ping` seule garde l'ancien comportement (mention sur le premier message). Une mention de rôle ne notifie que sous la forme `<@&ID>` — en clair (`@MonRôle`) elle reste du texte mort.
- **Limites Discord** : 4096 car./embed, 6000 car. cumulés → au-delà de 5200 car. (FR+EN), le script scinde en deux messages au lieu de tronquer.
- **Convention** : committer `announce.md` **seul**. S'il part avec des modifs de site, celles-ci glissent simplement sur l'annonce suivante.
- **Secrets** : `secrets.DISCORD_WEBHOOK`. `vars.SRC_LANG` n'est plus utilisé.

## 9. Conventions & pièges connus

**Conventions**
- **Manifeste unique** : ajouter une catégorie / un outil = éditer **uniquement site-config.js**. SITE.nameetSITE.home alimentent le logo du header. (jamais coder la nav en dur).
- **Nouvelle page = ne pas oublier `js/footer.js`** en dernière balise `<script>` (et une ligne dans `sitemap.xml`). Seule `pets.html` en est volontairement dépourvue. **Ne pas oublier non plus le bloc drawer figé** (cf. « maillage sans JavaScript » plus bas) : le recopier depuis n'importe quelle page existante, juste **avant** `<script src="js/site-config.js">`.
- **Fichiers de données : cache revalidé, jamais servi tel quel.** GitHub Pages sert `data/*.json` avec un cache de 10 minutes. Le HTML d'une page NEUVE, lui, n'est jamais en cache : un visiteur revenu dans cette fenêtre récupérait donc la page neuve avec l'ANCIENNE liste de boutiques, et lisait « Shop introuvable » sur une page pourtant en ligne — panne observée à la mise en ligne du Magasin du Théâtre, et reproduite à l'identique (barre des boutiques vide, vignette vide, titre resté anglais : tout découle de la boutique introuvable, `SP.kind` restant indéfini). `shop-core.js` passe donc ses 5 `fetch` par `scFetchData()`, qui ajoute `cache:'no-cache'` : ce n'est PAS une désactivation du cache mais une **revalidation** — 304 de quelques octets tant que le fichier n'a pas bougé, contenu neuf dès qu'il bouge. **Tout nouveau `fetch` de données doit passer par là** ; les autres fichiers (`heroes_db`, `pets_db`, `changelog`…) ont encore le comportement par défaut, moins visible faute de message d'erreur, mais tout aussi périmable.
- **Fichiers JS : jamais de nouveau nom global appelé d'un AUTRE fichier.** Les `<script>` du site n'ont aucun cache-busting, et le navigateur cache chaque fichier séparément : un visiteur de retour peut très bien charger le nouveau `shop-items-euro.js` avec l'ancien `shop-core.js`. Si la page appelle alors une fonction ajoutée en même temps qu'elle dans le core, c'est un **`ReferenceError` en plein rendu** — le tableau, déjà écrit, reste à l'écran avec les ANCIENS chiffres, pendant que tout ce qui suit disparaît en silence : encadré des règles, et surtout le branchement de l'aperçu au survol, qui ne se fait jamais. Panne observée à la mise en ligne des prix par pack (gemme à 0,0004 $ au lieu de 0,0007 $, aperçus morts), invisible en local puisque rien n'y est en cache. **Règle** : une page n'appelle que des noms globaux qui existaient DÉJÀ dans la version précédente du core ; un nouveau paramètre sur une fonction existante passe sans risque (le vieux code l'ignore et retombe sur son défaut — faux mais affiché, et corrigé au rechargement suivant), un nouveau NOM ne passe pas. D'où `iePackPriceOf()` / `ieBasisPrice()` dans `shop-items-euro.js`, qui enveloppent `scEurPackPrice(pid)` plutôt que d'appeler directement les `scEurRawPrice()` / `scEurBasisPrice()` nés avec eux. Les fonctions neuves du core restent libres de s'appeler entre elles : elles arrivent dans le même fichier, donc toujours ensemble.
- **Adresses sans `.html`, partout.** GitHub Pages sert `foo.html` aussi bien sous `/foo` que sous `/foo.html` : la même page a donc deux adresses, et c'est le `canonical` qui décide laquelle est indexée. La forme retenue pour tout le site est **la courte**. Concrètement : `X.html` → `/X`, et **`dir/index.html` → `/dir/`** (avec la barre finale — c'est l'adresse d'un dossier, pas `/dir/index`). Doivent porter la forme courte **ensemble**, sinon ils se contredisent et Google suit le `canonical` : `canonical`, les `hreflang`, `og:url`, le fil d'Ariane JSON-LD, le `sitemap.xml`, `llms.txt`, les `href` de `data/changelog.json`, **et tous les liens internes** — ceux écrits en dur dans les pages comme ceux fabriqués par le JS (`site-config.js`, `scShopHref()` dans `shop-core.js`, `hub.js`, le drawer de `header.js`, `HDR_ACTIVE_HREF`). **Deux exceptions**, et deux seulement : `404.html` (page spéciale de GitHub Pages, servie à n'importe quelle profondeur) et `google55512fe842dbeeaf.html` (jeton de vérification, dont le nom EST la preuve). Les FICHIERS, eux, gardent leur `.html` sur le disque : seules les adresses changent. **Test local** : un simple `python3 -m http.server` ne résout PLUS les liens internes, puisqu'il ne connaît que les noms de fichiers — servir le repo avec un serveur qui essaie `X.html` quand `/X` est demandé, comme le fait GitHub Pages, sinon toute la navigation paraît cassée en local alors qu'elle est bonne en ligne.
- **`<base href>` relatif, jamais absolu** : les pages en sous-dossier déclarent `<base href="../">` (1 niveau, `shop/*`) ou `<base href="../../">` (2 niveaux, `database/*/*`), selon leur profondeur. Le site est ainsi **insensible à son chemin de déploiement** : il fonctionne à la racine du domaine, sous `/Kingshot_Toolbox/`, et sur un serveur local à n'importe quel préfixe. Ne jamais revenir à un chemin absolu (`/Kingshot_Toolbox/`) : c'est ce qui rendait tout changement d'URL risqué.
- **Lien vers l'accueil = `./`, jamais `index.html`** (fils d'ariane, logo du header via `SITE.home`). Les deux servent la même page, mais la **canonique est la racine** : viser `index.html` envoyait 100 % du maillage interne sur l'URL qu'on demande à Google d'ignorer (SEMrush mesurait un ILR de 100 sur `/index.html` contre 9 sur `/`) et dédoublait l'accueil dans Analytics (`/` et `/index.html` comptés séparément). `./` se résout via le `<base href>` de chaque profondeur : la règle d'insensibilité au chemin de déploiement est préservée. Les `index.html` de sous-dossier (`database/*/index.html`) ne sont **pas** concernés : leur canonique porte déjà `index.html`, les trois listes (lien, canonique, sitemap) y sont cohérentes.
- **Google Analytics (GA4, `G-M1QG4XSD3K`)** : extrait officiel `gtag.js` collé **verbatim** dans le `<head>` de chaque page, juste après le script de thème (qui doit rester premier). Présent sur les 66 pages HTML, `404.html` comprise ; **seule exception `google55512fe842dbeeaf.html`**, le jeton de vérification Search Console. L'identifiant est donc dupliqué 66 fois : le changer = un remplacement global. Vérifié : le site se rend normalement quand le script est bloqué (bloqueur de pub).
- **Thème appliqué dans le `<head>`, avant le 1er rendu** : un `<script>` inline juste après `<meta charset>` lit `hub_theme` et pose `data-theme` sur `<html>`. Sans lui, la page s'affiche avec le `data-theme="dark"` écrit en dur, puis bascule quand `header.js` se charge **en fin de `<body>`** — et comme `body` porte `transition: background-color 0.3s`, le flash sombre est *animé*, très visible en navigation mobile. Mesuré : fond encore en transition à 150 ms avant correctif, clair dès 60 ms après. Toute nouvelle page doit porter ce script.
- **Le mode d'emploi d'une page se complète, il ne se réécrit pas.** `shop-page.js` pose UNE aide pour les onze boutiques ; celle du Théâtre a sept points de plus que les autres n'ont pas. Plutôt que d'écrire dans le fichier partagé des étapes qui ne parlent qu'à une page, il construit sa configuration puis appelle `window.spHelpExtras(cfg)` si un module l'a posée — `js/shop-theater.js` y ajoute son chapitre (`cfg.sections`), et la modale de `help.js` rend chaque chapitre sous son propre titre, numéroté à part. Absente, la fonction ne change rien : les dix autres boutiques gardent exactement l'aide d'avant. **Poser le hook au premier niveau du fichier, jamais après un `await`** : `shop-page.js` construit son aide après le chargement des données, mais un module qui attendrait de son côté passerait après lui.
- **Un greffon qui recopie les règles de `seCompute` dérive, toujours.** L'optimiseur du Théâtre recalculait de son côté ce que le plan avait déjà versé, à partir de `plan.buys` et des missions du fichier. Deux règles y manquaient aussitôt : les **achats faits ailleurs** (`outsideBuys`, que ce même lot venait pourtant d'activer sur cette page en ajoutant une mission `requiresPurchase`) — 60 amulettes de trop dans le solde « en poche », le seul chiffre que la page déclare comparable au jeu —, et les **lignes décochées** dans le détail des gains, qui faisaient accuser le fichier de données d'une omission inexistante. Le calcul borné (`seCompute(upTo)`) supprime la duplication : une seule source de vérité, et les règles futures de `seCompute` (packs `once`, pass qui doublent les missions, `freeDailyPack`, `waypost`) suivront toutes seules. **Décocher une ligne du détail** reste un cas à traiter à part : les revenus tombent à zéro pendant que les dépenses restent, et le solde devient légitimement négatif — le dire, plutôt que crier à la donnée manquante.
- **« Ne pas encaisser » ne veut pas dire « pousser ».** Une politique optimale qui renvoie « pas d'encaissement » le fait aussi bien parce que pousser est meilleur que parce qu'**aucune action n'est possible** — budget insuffisant pour une exploration, ce qui est l'état normal de fin d'événement. Le verdict conseillait alors une exploration impayable. Toute lecture d'un `argmax` doit distinguer « l'autre branche gagne » de « aucune branche n'est jouable ».
- **Un état relu du `localStorage` indexe des tables : le borner avant, pas après.** `floor` et `pity` entrent directement dans les tableaux typés du moteur. Un état hors bornes — reliquat d'une version précédente, ou sauvegarde importée depuis un autre appareil, ce que la Sauvegarde Globale rend possible — lisait au-delà du `Float64Array` et affichait des « NaN% ». Le bornage se fait au chargement, avant tout calcul.
- **Un plan d'événement projette l'avenir : il ne se compare pas au jeu.** La grille d'achat couvre TOUS les jours, y compris ceux où les packs ne sont pas encore achetables. Le total qu'elle verse est donc « ce que l'événement rapportera en tout », pas « ce que j'ai ». L'optimiseur du Théâtre affirmait qu'un écart entre son total et le jeu prouvait une erreur de données — c'était faux et systématique dès le 2ᵉ jour. Il distingue désormais **en poche aujourd'hui** (`total − dépensé − à venir`, le seul chiffre comparable au jeu, `stFutureIncome()` bornant l'avenir au jour d'événement en cours) et **à dépenser d'ici la fin** (le budget stratégique). Toute page greffée qui lit `c` d'un plan doit se poser la question : ce chiffre décrit-il le présent ou la projection ?
- **Un stepper ne sait pas ce qui s'est passé en jeu.** Reporter automatiquement le coût d'une exploration sur le compteur d'amulettes dépensées est tentant : +1 échec à l'étage 3, +20 dépensées. Mais une montée vaut **+1, +2 ou +3 étages pour une seule exploration payée** — facturer chaque clic du stepper d'étage compterait deux ou trois explorations là où le jeu n'en fait payer qu'une, et le compteur dériverait dans l'autre sens. D'où des **boutons d'action** (`stAct()`) qui disent ce qui vient d'arriver — *échouer*, *monter +1 / +2 / +3*, *encaisser* — le joueur choisissant lui-même la hauteur du saut, une seule exploration étant facturée quelle qu'elle soit. Les steppers restent à côté une correction libre et gratuite : séparer « j'ai joué » de « je corrige ma saisie » est ce qui rend le report fiable.
- **Un seuil de décision dépend de l'état, l'afficher comme une règle rend la page incohérente.** L'optimiseur annonçait « en dessous de 520 amulettes, encaisse » à côté d'un conseil « pousse » avec 388 — deux phrases qui se contredisent en apparence. Le seuil affiché était celui de l'étage 2 sur un compteur neuf ; à l'étage 3 avec 2 échecs il vaut **20**. Le compteur de garantie écrase tout : à l'étage 2 il fait passer la bascule de 519 à 8, parce que la montée suivante est presque acquise. `stFlipBudget()` prend donc l'étage et le compteur en argument, et la phrase nomme l'état auquel elle s'applique.
- **Un budget qu'on plafonne à zéro cache le bug qui l'a rendu négatif.** L'optimiseur du Théâtre déduisait les amulettes restantes du plan (`total − dépensées`) et écrasait un résultat négatif par `Math.max(0, …)`. Or un reste négatif est **impossible en jeu** : il ne veut pas dire « zéro », il prouve que le modèle ignore une source d'amulettes. Le plafond a masqué le cadeau d'ouverture de l'événement pendant deux jours — la page affichait 0 là où il en restait 8, et l'écart de 10 ne se voyait nulle part. Règle générale : ne jamais borner une valeur dérivée dont le dépassement est un diagnostic.
- **`style.css` raye TOUTES les tables : une classe seule ne surligne pas une ligne.** `tbody tr:nth-child(even) { background-color: var(--table-row-alt) }` est une règle globale de spécificité (0,1,2) — un `.ma-classe` posé sur un `<tr>` (0,1,0) perd contre elle une ligne sur deux. La mise en avant « Meilleure » du tableau d'encaissement est ainsi restée invisible : elle tombait sur une ligne paire. Qualifier comme le fait déjà le survol du même fichier — `.sxe-grid tbody tr.ma-classe` (0,2,2) l'emporte. **Et doubler la règle sur `td.c-pack`** : cette colonne est `position: sticky` avec un fond OPAQUE, aucun fond de ligne ne passe dessous, sinon la bande démarre une colonne trop loin.

Une valeur absente se teste, elle ne se replie pas sur un chiffre qui, lui, veut dire quelque chose.
- **Une pastille `.sx-fact` en `nowrap` peut faire défiler toute la page.** `.sx-fact` porte `white-space: nowrap` — parfait dans l'en-tête de boutique, où les faits sont courts (« Fin dans 5 j »). Dans `.sxe-toolbar`, le plus long (« Amulettes Fantaisie dépensées » et son compteur de paliers) dépasse à lui seul la largeur d'un téléphone ; comme un élément flex ne rétrécit jamais sous son contenu (`min-width: auto`), le `flex-wrap: wrap` du conteneur n'y peut rien et c'est la PAGE qui s'élargit. Mesuré : **52 px** de débordement horizontal sur le Magasin du Théâtre, **18 px** sur le Stand d'Aventure, 0 sur la Caravane du Dragon (ses libellés sont plus courts) — d'où un bug qui paraissait propre à une page alors qu'il tenait à la longueur d'un mot. Corrigé par `.sxe-toolbar .sx-fact { white-space: normal; flex-wrap: wrap; max-width: 100% }` : la pastille se replie au lieu de pousser la page, sans rien changer sur grand écran (barre d'outils mesurée identique au pixel, 1178 × 84). **Le symptôme trompe** : le premier élément trop large qu'on trouve est `#hdr-drawer-overlay`, en `position: fixed; width: 100%` — il ne déborde pas, il suit la largeur du document déjà élargi. - **Une règle déduite qui passe au-dessus du prix du marché est un signal, pas un détail.** Depuis le pack **Privilège de Recherche** (160 caisses de ressources Lv3 pour 12 €, soit **0,075 €** l'unité), le relevé chiffre cette caisse à moins de la moitié de ce qu'en dit la règle déduite : **0,160 €**, soit 100 × la caisse Lv1, elle-même alignée sur le pain pondéré ×0,25. `derived` l'emportant sur le relevé, c'est 0,160 € qui s'affiche. L'un des deux est faux — le facteur ×100 ou l'alignement de la Lv1 — et seul le jeu peut trancher : ouvrir une Lv1 et une Lv3, comparer les quantités de ressources. **Non tranché** ; laissé tel quel plutôt que corrigé au jugé, parce que toucher au facteur déplacerait d'un coup les trois caisses sur toutes les boutiques.
- **`localStorage` = par origine, pas par domaine logique** : un changement de nom de domaine rend **toutes** les données utilisateur invisibles (héros, recherches, profils, thème, langue). Elles ne sont pas effacées, elles restent sur l'ancienne origine. C'est ce qui s'est produit au passage à `kingshottoolbox.com`. Deux conséquences : les données laissées sur une ancienne origine ont une **date de péremption d'environ une semaine**, et sur iPhone il n'existe **aucune console** — la seule reprise possible passe par une page servie depuis l'ancienne origine (dépôt `aistra91-ks.github.io`). Toute future page de reprise doit donc offrir un export **par presse-papier** et un import **par collage de texte**, Safari bloquant parfois les téléchargements déclenchés par script — c'est ce que faisait `migrate.html`.

Sans effet depuis le passage au domaine propre (plus aucune clé à plat), mais à corriger si le système de profils est retouché.

  **Le drawer suit désormais la même règle** : le bloc `#hdr-drawer-overlay` + `#hdr-drawer` (avec sa `nav.drawer-nav` et les 13 liens outils/BDD, libellés EN) est **figé en dur dans les 65 pages qui chargent `header.js`**, placé **avant** les `<script>` de fin de page. L'ordre est impératif : `header.js` ne crée le drawer que s'il ne le trouve pas (`if (!document.getElementById('hdr-drawer'))`), et ce test s'exécute avant que le parseur n'ait atteint un bloc placé plus bas — d'où **deux drawers** superposés si on l'insère après les scripts (erreur commise puis corrigée). `hdrBuildDrawer()` remplace ensuite le contenu par sa version complète (icônes, profil, langue, thème) : le DOM final est identique au commentaire HTML près.
  Gain : les 8 outils passaient pour des **culs-de-sac** en HTML brut (1 lien entrant, **0 sortant**) ; ils comptent maintenant 64-65 pages entrantes. Ça ne change rien pour Google, qui exécute le JS et voyait déjà tout — mais **les crawlers d'IA (GPTBot, OAI-SearchBot, ChatGPT-User) ne l'exécutent pas**, et c'est aussi ce qui explique l'ILR de 18 mesuré par SEMrush sur les outils : un audit sans rendu JS. Signe qui ne trompe pas, cet audit n'avait pas trouvé `about.html` ni `changelog.html`, liées uniquement depuis le pied de page injecté.

- **`<link rel="canonical">` absolu sur chaque page** : `https://kingshottoolbox.com/<chemin>`, l'accueil pointant sur la racine (sans `index.html`). C'est la **seule URL absolue** du HTML — tout le reste reste relatif. Toute nouvelle page en porte une, et son URL doit correspondre **exactement** à sa ligne de `sitemap.xml` : les deux listes se vérifient en 1:1 (65 = 65 aujourd'hui).

Message **en anglais** : titre en langage courant + corps compréhensible par un joueur non développeur, dans le budget de longueur du §7.Dans `github.dev`, la boîte de message est multiligne (**Shift+Entrée**) : ligne 1 = titre, ligne vide, puis le corps. Tout mettre sur une seule ligne rend l'intégralité de la news **en gras** sur Discord (le corps devient partie du `subject`).

**Pièges déjà rencontrés**
- **Dépendance `GlobalLang` non définie** : `lang.js` doit être chargé **avant** tout script qui appelle `GlobalLang` ; toujours garder le fallback `window.GlobalLang ? GlobalLang.get() : 'FR'` (déjà en place dans header/help/backup). Ordre de chargement critique.
- **Fonction `getRawNumber` manquante** : helper local à `beartrap.js` (nettoie espaces + `parseInt`). N'existe **pas** globalement — ne pas l'appeler depuis un autre script sans la (re)définir.
- **Formatage des nombres dépendant de la locale** : l'UI formate les milliers via `toLocaleString('fr-FR')` (espaces). Les inputs numériques FR **refusent le `.`** ; côté saisie, nettoyer (`replace(/\D/g,'')` / strip espaces) **avant** `parseInt`/`parseFloat`. Ne pas parser directement `el.value` formaté.
- **Gestion d'erreurs des `fetch`** : tous les chargements de données sont des `fetch('data/….json')` relatifs (sensibles au chemin de déploiement Pages). Toujours vérifier `response.ok` et prévoir un message clair (ex. TrueGold affiche un diagnostic « le fichier existe-t-il ? »). Un `data/` mal résolu casse silencieusement l'outil.
- **Embeds Discord fusionnés** : deux embeds d'un même message qui portent la **même `url`** sont regroupés par Discord en un seul bloc, et la description du second est perdue (c'est le mécanisme d'affichage multi-images). Ne jamais mettre `url` sur les embeds FR/EN de `announce.js` — le lien vers le site passe par `author`.
- **Équipement Exclusif d'un héros (`widget`)** — trois pièges, tous silencieux :
  1. **5 paliers pour un sélecteur qui va à 10** : la Conquête se lit aux niveaux **impairs** (1/3/5/7/9), l'Expédition aux **pairs** (2/4/6/8/10) — `getWidgetEffectValue()` (`caserne.js`). Un `levels[]` de 10 entrées ferait donc afficher une valeur sur deux. Au niveau 0 (et 1 côté Expédition) l'effet vaut `"0%"` et s'affiche grisé.
  2. **Substitution des « X »** (`formatWidgetDesc`, `caserne.js`) : une phrase à **une** valeur voit **tous** ses « X »/« X% » remplacés (regex globale) — ne jamais laisser un X littéral ailleurs dans le texte, dans aucune des deux langues. Une phrase à **deux** valeurs utilise le format `"(a,b)"` — **virgule**, contrairement au `"(a;b)"` des Experts (§6) — et les valeurs sont injectées **dans l'ordre du texte**. Le `%` fait partie de la valeur : écrire `X%` dans la phrase et `"15%"` dans `levels`.
  3. **Les icônes sont résolues par `name.EN` exact** : `img/widgetname/<widget.name.EN>.webp` (l'arme) et `img/widgetskill/<effect.name.EN>.webp` (les 2 effets). Renommer ou corriger un `name.EN` casse l'image sans erreur — d'où la coquille `Offenseive Defense` (Yang) qu'il faut **conserver** telle quelle.
  Un héros sans `widget` ne casse rien : `renderModalWidget()` masque le conteneur, et `modal-tabs.js` retire l'onglet « Équipement » du mode mobile (panneau vide). *C'est ce qui a rendu invisible pendant un temps l'absence des équipements gen 7.*

## 10. Tests

**`node --test`** à la racine du dépôt. Rien à installer, rien à construire — c'est le lanceur de Node lui-même, et les tests ne chargent que des fichiers déjà servis par le site.

**Comment ça marche.** Le site n'a ni modules ni build : `js/*.js` pose des fonctions globales que le navigateur assemble page par page. `tests/harness.mjs` reproduit ça dans un contexte `vm` — les scripts y sont chargés **sans être modifiés**, dans l'ordre du HTML, avec trois substituts : `fetch` lit `data/` sur le disque, `localStorage` est en mémoire (donc chaque test part des valeurs par défaut), et `document.getElementById` rend `null`, ce qui fait sortir les IIFE de fin de fichier avant tout rendu. C'est ce qui permet de tester **le code réellement servi** sans lui ajouter le moindre `export`.

Conséquence à connaître : les `let` de premier niveau d'un script vivent dans la portée lexicale du contexte, pas sur son objet global. On ne les lit et ne les écrit donc qu'**à l'intérieur** du contexte, via `run(ctx, '…')`.

**Ce qui est couvert.** Les deux calculs où une régression serait invisible à l'écran et coûteuse pour le joueur :
- **Valorisation d'événement** (`seCompute`) — les contrôles réels de §7, jusqu'ici vérifiés à la main une seule fois : Caravane du Dragon 4 jours + achat déclaré → **230 essences** (et 195 sans, ce qui prouve d'où viennent les 35), Stand d'Aventure F2P 5 jours → **32 388 gemmes**, plus l'invariant « autant de Points de Vente que de Pièces d'Aventure par source ».
- **Tirage du Théâtre** (`ftClimbCostFrom`, `ftComputeReach`, `ftAttemptsFrom`) — la forme close comparée à une **simulation Monte-Carlo qui ne partage aucune ligne avec elle**. Le générateur est **grainé** : à graine fixe le résultat ne bouge pas, donc un test qui échoue signale un vrai écart, jamais un coup de malchance.

**Ajouter un test.** Un contrôle chiffré écrit en prose dans ce fichier est déjà un test — il ne lui manque que d'être exécutable. Le transcrire vaut mieux que d'en inventer un nouveau : il vient d'un relevé en jeu.

**Une règle.** Un test qui ne peut pas échouer ne protège rien. Après en avoir écrit un, casser volontairement le code qu'il couvre et vérifier qu'il vire au rouge — c'est ce qui a validé la première série.
